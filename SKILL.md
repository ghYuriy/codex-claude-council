# Codex–Claude Council

The current Codex owns the task, edits and final report. Claude independently investigates primary material, challenges conclusions and verifies completed blocks. Neither model defends its authorship or tries to win. Judge alternatives by correctness, effectiveness, appropriateness, safety and usefulness for the original task. Agreement and confidence are not evidence.

## Start with the actual task

1. Read [references/protocol.md](references/protocol.md) for commands, intake and recovery. Use `$HOME/.local/state/codex-claude-council` as the fixed default state root for both creation and discovery unless the user or project specifies another. Preserve an existing task's actual root and record its full task path in the handoff. For a resume request, run `list` and `status`; keep the identity, sessions, source requirements and counters. If no matching task is found, inspect the prior handoff and known project settings, then ask for the missing location if needed. Never substitute `init` for an unfound task. Read [references/quality-contract.md](references/quality-contract.md) before decomposing a new task or assessing disputed findings. Existing version-1 tasks retain their recorded scope and budgets; do not claim they retroactively received version-2 checks.
2. Inspect project instructions, actual sources and existing implementation/check patterns before choosing a solution. Reuse what fits the requirements; load supporting references when relevant rather than importing a whole toolkit. Preserve the existing `claude -p` stdin/JSON/UUID transport and subscription login. Do not reinstall CLI, change model/auth/environment, add API fallback, widen permissions, launch another Codex or recursively delegate. [references/local-transport.md](references/local-transport.md) describes the transport requirements and compatibility limits.
3. Preserve the original user request and all acceptance criteria. Decompose every task into macro outcomes and concrete micro obligations. For a small repair one block with a few meaningful leaves is enough. A leaf identifies its requirement, action, observable result and applicable check. Continue decomposition while a material behavior, dependency, uncertainty or acceptance obligation remains ambiguous; do not invent work merely to make the plan longer.
4. For a substantial change, trace the affected entry points, callers, data/state transitions, consumers and integration routes using actual source evidence. Record related checks in `work_plan.impact`. For a local change, state why a narrower check is sufficient. A passing function test cannot prove that its caller or whole user journey still works.
5. Initialize one durable task outside the product worktree. Choose finite total launches, call timeout and task deadline from the planned blocks, investigations and expected repair work. New tasks do not require arbitrary small DESIGN/CONSULT/REVIEW ceilings. Optional phase caps are supported if useful. Missing finite limits fail closed. Do not reset counters by changing topic, stage, task ID or state root.

## Collaborate when it changes the outcome

6. Use DESIGN for a significant design decision and CONSULT for a difficult bug, conflicting evidence, consequential uncertainty or an analytical question, including during implementation. Use the [focused questions](references/quality-contract.md#focused-questions-within-the-existing-workflow) when a conclusion, decisive assumption or likely failure needs examination. Combine relevant questions in the existing discussion; they do not create modes, stages or extra calls by themselves. Give Claude original requirements, source files, observations and limits. The first assessment advertises only primary material and the evidence subtree, with instructions not to inspect state, issues or previous model reports. This reduces exposure to earlier opinions; it is not filesystem read confinement. Codex forms its own assessment separately. An obvious local repair does not need a ceremonial design debate.
7. After independent inspection, compare concrete claims. Continue the saved session with `--exchange` when disagreement needs a substantive response: question, positions, evidence, alternatives and a distinguishing next check. Facts require evidence; proposals and testable questions must be labeled. A hypothesis may guide an experiment, but must not become a factual conclusion, product behavior or passing check without verification. Ask for relevant inspectable arguments, not hidden chain of thought.
8. Every follow-up must resolve an identified uncertainty through new evidence, a test, a repair, an evidence-backed rejection or a precise missing fact. Keep enough detail and full source references for the other model to assess it. Do not replace primary material with a persuasive summary, force two-word responses, impose performative word quotas, or continue merely to obtain agreement. Structural repetition is detected by the controller; semantic repetition still requires judgment.

## Implement and verify

9. Codex implements the simplest complete solution and retains all requirements. Both models are strictly prohibited from inventing facts, silently generalizing a partial check to a whole system, offering superficial analysis, weakening tests or scope, hiding unknowns, substituting mocks/TODOs for required behavior, or calling unverified work complete. Simplicity means fewer unnecessary mechanisms while preserving behavior, data and necessary safeguards. It does not permit a partial fix.
10. Select checks by observable obligations and realistic failure modes. Reuse the project's verification commands; exercise the actual entry point or user interaction when the claimed outcome depends on it. Each added test, abstraction, configuration or dependency needs a concrete reason tied to the task. Do not produce hundreds of redundant assertions, exhaustive hypothetical matrices or future infrastructure for a small change. Do not omit a meaningful check merely to reduce the count.
11. Execute declared checks through `check`; capture manual/UI/document observations through `attest` with the actual method, artifact, current snapshot and limits. For a bug, reproduce first when possible and repeat the distinguishing case after repair. For substantial changes, also exercise the recorded affected routes. Missing access or data remains unknown.
12. At the end of every macro block, run REVIEW and `checkpoint`. The first REVIEW session is independent of DESIGN/CONSULT opinions. Later REVIEW calls resume that exact session to verify issue closure and repair regressions. Freeze the worktree while Claude reads it; content changes invalidate the result. Full relevant files, diff, requirements and evidence remain available; no silent truncation.
13. Record an action for every issue. An author's repair remains `FIXED_PENDING_CHECK` until new related check evidence and reviewer confirmation. A harmful suggestion is disputed with a counterexample and may become `REJECTED_WITH_EVIDENCE`; do not change correct behavior just because the reviewer requested it. Preserve issue history. Read [references/review-contract.md](references/review-contract.md) for exact closure and evidence rules.

## Stop honestly and resume safely

14. A shared evidence-supported decision can select either model's proposal, a different proposal, or an explicit unknown. It is not a compromise of preferences. If no new useful check exists, stop rather than rephrase positions. An unresolved defect yields `BLOCKED`; conflicting goals, material residual risk or needed authorization yield `NEEDS_DECISION` with alternatives and consequences. Each discussion must reach its own evidenced CLEAR response before checkpoint/final acceptance; another session's clean result cannot erase its unresolved question. Resume that same discussion with the new evidence or the actual saved user decision. Only the user can accept a material risk or authorize a budget extension; a model's CLEAR response never supplies authorization. An extension is recorded on the same task and never resets consumption.
15. Use `stop` to cancel the owned run and `recover` after interruption; poll `status`, not the model. Do not infer a hang from quiet stdout. Old passing checks cannot replace interrupted new ones. The controller preserves raw outputs, sessions and counters and never promotes a partial answer to successful review. At handoff, include the task path, current block, open questions, evidence locations and next useful check. Resume from the saved state; a summary is an index, not replacement evidence.
16. Finish with the integration criterion for multi-block tasks, `finalize` and `status`. Only current `PASSED` establishes process acceptance. `CLEAR`, `REVIEWED`, exit 0 or an empty issue list alone do not. Report checked behavior, evidence, unresolved limits and accepted risks. After changes, refresh stale checks/reviews within the same task.

This is an editable local workflow, not an OS sandbox or a proof of semantic correctness. Read/search tool restrictions, hashes and JSON validation do not prove that a model's reasoning is true. Do not promise bug-free work. Use the project's existing security boundaries and release checks where required.
