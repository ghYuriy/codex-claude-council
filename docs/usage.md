# Использование в разных проектах

Глобальный навык доступен из разных проектов Codex на той же машине. Он не привязан к языку программирования, фреймворку или одному репозиторию. Откройте правильную папку проекта, напишите «подключи Claude как помощника» и опишите задачу. Указывать `$codex-claude-council` необязательно; явный вызов по-прежнему доступен.

Codex подхватывает изменения навыков автоматически. Если обновление не появилось, перезапустите приложение. Подробнее в [справке Codex](https://learn.chatgpt.com/docs/build-skills#how-codex-uses-skills).

Перед использованием установите навык по [инструкции](../README.md#установка-в-codex) и убедитесь, что вход в Claude Code работает.

## Что делает пользователь, а что делает Codex

Пользователь описывает желаемый результат, ограничения и известные симптомы. Codex читает материалы, составляет проверяемый план, выбирает соразмерные проверки и конечный бюджет, сохраняет состояние и вызывает контроллер. Пользователю не нужно знать названия внутренних фаз или вручную создавать JSON.

Уточнение потребуется, если существенный факт нельзя установить из доступных материалов. Обычные обратимые технические решения не требуют остановки работы. До ответа на существенный вопрос продолжается только независимая часть задачи.

## Разработка новой функции

```text
$codex-claude-council Добавь сохранение черновика формы между перезагрузками.
Сначала изучите с Claude текущие переходы состояния и требования к данным.
Разложи работу на проверяемые блоки и шаги. Не меняй существующие правила
отправки формы. После каждого крупного блока проведи независимое ревью
Claude, а в конце проверь весь сценарий восстановления и отправки черновика.
Не добавляй сервер или новую зависимость без установленной необходимости.
```

У этого условного запроса макроуровень может включать хранение, восстановление и интеграцию с отправкой. Микроуровень задаётся после чтения текущего проекта: например, изменение поля, сохранение, перезагрузка, восстановление и корректное очищение после успешной отправки. Это пример структуры, а не готовая архитектура для любого проекта.

## Сложная ошибка

```text
$codex-claude-council Найди причину, почему событие иногда обрабатывается
дважды. Сначала собери фактическую последовательность вызовов и воспроизведи
случай. Пусть Claude независимо изучит первичные данные и предложит
различающие проверки. Не принимайте предположение о повторном запросе
за причину, пока оно не подтверждено. После исправления проверьте связанные
обработчики и передайте завершённый блок на независимое ревью.
```

Claude можно подключить для разбора нового сложного вопроса в середине работы, даже если предыдущий этап уже проверен. Все обсуждения используют общий бюджет задачи.

## Аналитика или решение без изменения кода

```text
$codex-claude-council Сравните два предложенных процесса обработки обращений
по приложенным материалам. Сначала независимо проверьте исходные факты,
затем сопоставьте варианты по трудозатратам, риску ошибок и сохранению данных.
Не придумывайте отсутствующие цифры и не подменяйте неизвестное оценкой.
Проверьте, следует ли каждый существенный вывод из данных, какая непроверенная
предпосылка может изменить выбор и как выбранный процесс может дать сбой.
Сформулируйте вывод только в пределах подтверждённых данных; отдельно
покажите, каких фактов не хватает для окончательного решения.
```

Для анализа Codex сохраняет источники и основания выводов. Если существенный факт недоступен, он указывает, какой вывод пока нельзя подтвердить. Согласие моделей не заменяет исходные данные.

Например, в условном отчёте число обращений снизилось после изменения процесса. Само совпадение по времени ещё не доказывает, что причиной стало изменение: могло уменьшиться число пользователей. Проверка должна различить эти объяснения. Если нужных данных нет, причинный вывод остаётся неподтверждённым. Для этого не нужно создавать отдельный этап или повторять все вопросы при каждой простой правке.

## Постоянное правило в одном проекте

Если вы хотите применять навык ко всем существенным задачам определённого проекта, можно **по вашему запросу** добавить в его `AGENTS.md` небольшой раздел:

```markdown
Для существенной разработки, сложных ошибок и аналитических решений
используй глобальный skill codex-claude-council. Текущий Codex ведёт работу;
Claude независимо исследует сложные вопросы и проверяет каждый завершённый
макроблок. Сохраняй исходные требования, доказательства и конечный бюджет.
Не запускай дополнительный Codex и не создавай рекурсивное делегирование.
```

Это правило не нужно копировать целиком из протокола. Установка глобального навыка сама по себе не изменяет `AGENTS.md` ваших проектов.

## Технический пример для проверки установки

Из корня клонированного репозитория:

```bash
COUNCIL="$(pwd)/scripts/council.py"
DEMO_ROOT="$(mktemp -d "${TMPDIR:-/tmp}/council-demo.XXXXXX")"
mkdir "$DEMO_ROOT/project"
cp examples/demo/ratio.py examples/demo/test_ratio.py "$DEMO_ROOT/project/"
python3 "$COUNCIL" init --lead codex --project "$DEMO_ROOT/project" --state-root "$DEMO_ROOT/state" \
  --conversation-root "$DEMO_ROOT/conversations" --intake examples/intake.json
```

Отдельный `--conversation-root` не даёт демонстрации привязать текущую беседу Codex к временной папке, если команду запускает сам агент. Последняя команда выводит абсолютный путь задачи. Для дальнейших команд сохраните **этот фактический путь** в переменную `TASK`. Не подставляйте выдуманный идентификатор. Проверка самой функции:

```bash
python3 "$COUNCIL" check --task "$TASK" --id unit --timeout 30 -- python3 -B -m unittest -v
```

Реальное ревью, в отличие от автономных тестов контроллера, обращается к Claude и расходует соответствующий лимит:

```bash
python3 "$COUNCIL" call --task "$TASK" --phase REVIEW --stage implementation --goal "Независимо проверь исходное требование, код и фактические результаты unit."
python3 "$COUNCIL" checkpoint --task "$TASK" --stage implementation
python3 "$COUNCIL" finalize --task "$TASK"
python3 "$COUNCIL" status --task "$TASK"
```

Это временная демонстрация. Для настоящей работы используется постоянный каталог `$HOME/.local/state/codex-claude-council`, если пользователь или проект явно не задали другой путь вне проекта. Существующая задача сохраняет прежний фактический путь. Если Claude обнаружит замечание, следуйте процедуре исправления из [протокола](../references/protocol.md), а не ожидайте автоматического PASSED от примера.

## Что получает помощник и что хранится

Это описание текущего поведения, а не обещание изоляции.

**Текст запроса.** Помощник получает `prompt.json`: исходную задачу, требования, план, сведения о проверках и пути к материалам. Инструкция критика и схема отчёта передаются один раз, через собственный канал транспорта: у Claude флагами `--append-system-prompt` и `--json-schema`, у Codex параметрами беседы через адаптер. Полный запрос вместе с инструкцией и схемой сохраняется в `request.json`.

**Доступ.** Claude-рецензент запускается с инструментами только для чтения (`Read`, `Grep`, `Glob`), без MCP-серверов, с отключёнными hooks и slash-командами; каталог доказательств добавляется через `--add-dir`. Codex-помощник работает в песочнице только для чтения. Делегированное исправление получает запись во всём проекте (`workspace-write`); список файлов из его плана контроллер сверяет с наблюдаемыми изменениями уже после выполнения, а изменения вне охвата снимка этим сравнением могут остаться незамеченными (подробнее в [repair-control.md](../references/repair-control.md)).

**Окружение.** Помощник входит только через сохранённый вход своего CLI по подписке: `/login` в Claude Code, `codex login` через ChatGPT. Других способов входа Council не поддерживает. Задачи, созданные начиная с 1.5.0, всегда запускают помощника с отфильтрованным окружением: пути, локаль, временный каталог, прокси и сертификаты, собственные настройки CLI (выбор модели и усилия, клиентский сертификат, отказ от телеметрии), расположение сохранённого входа (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) и имена, добавленные для задачи или вызова. Из собственных пространств имён CLI (`ANTHROPIC_*`, `CLAUDE*`, `OPENAI_*`, `CODEX_*`) проходят только перечисленные переменные, а добавить оттуда нельзя ни одной: любая версия CLI может читать там новые переменные, которые переключают на другой способ входа (ключ или токен API, другой адрес API, облачный поставщик) или несут идентификатор сессии ведущего. Команда с таким именем останавливается до запуска; так же отвергается `AWS_BEARER_TOKEN_BEDROCK` — токен входа через Bedrock вне этих пространств. Остальные добавленные имена передаются как есть: Council не отличает переменную проекта от переменной, которую CLI читает без своего префикса (например, `API_TIMEOUT_MS` у Claude), поэтому добавляйте только то, что нужно помощнику. Council фильтрует только окружение процесса, а сохранённый вход и файлы настроек CLI не меняет, поэтому сам CLI должен быть входом по подписке: сохранённый ключ API, другой поставщик моделей в `config.toml` Codex или поставщик, заданный в `env` настроек Claude, не поддерживаются. `/codex-claude-council:setup` считает Codex готовым только при входе через ChatGPT и поставщике моделей, который он прочитал как OpenAI. Он проверяет тот процесс Codex, к которому подключился: если для проекта уже работает общий процесс, setup сообщает его вход и настройки, а они могут быть прежними, если `CODEX_HOME` с тех пор менялся; помощник же всегда запускает свой процесс. Если вход не удался, `last_failure` покажет `AUTH` и подскажет войти через `/login` или `codex login` и повторить вызов. Задачи, созданные до 1.5.0, наследуют всё окружение, как раньше, и `COUNCIL_PASS_ENV` на них не влияет.

Добавить имя переменной можно тремя способами: при создании задачи — `init --pass-env NAME`; для существующей задачи — `env --task … --pass-env NAME`, счётчики и сессии при этом не меняются; только на один вызов — `COUNCIL_PASS_ENV=NAME1,NAME2`. Контроллер сохраняет только имена — в состоянии задачи, в `job.json` и в записи запуска; запись запуска перечисляет имена, которые передаёт Council, а система может добавить свои (в macOS — `__CF_USER_TEXT_ENCODING`). Значения он не записывает, но необработанный вывод CLI в каталоге задачи может их содержать. Если помощнику нужна переменная проекта, подсказка `last_failure` называет и команду `env`. Повтора с другим окружением или другим способом входа нет.

**Инструкции.** Пользовательские и проектные инструкции и настройки CLI загружаются по правилам самого CLI. На установленных CLI проверено: пользовательский и проектный `CLAUDE.md` у Claude и пользовательский и проектный `AGENTS.md` у Codex загружаются и при новом запуске, и при продолжении, а изменённый файл проекта при продолжении перечитывается. У Codex-помощника запускаются также пользовательские hooks и MCP-серверы Codex. Council их не изолирует; он только добавляет свою инструкцию критика.

**Расход.** Каждый запуск помощника записывает `usage`. У Claude это расход данного вызова из поля `usage` ответа CLI; накопленное по сессии `modelUsage` хранится отдельно. У Codex это разность накопленного по беседе счётчика в конце хода и до его начала; адаптер пишет счётчик в `usage.json` рядом с запуском, отдельно от контрольной точки сессии. Если ход не завершился, записанное значение — только нижняя граница (`complete: false`). Не полученное записывается как `null`, а не как ноль: запуск, прерванный до первого события расхода, продолжение без известной начальной точки, счётчик, который уменьшился внутри хода или оказался ниже последнего значения, которое видел любой прежний запуск той же беседы. Ответ Claude без одного из четырёх счётчиков или без `usage` сохраняется как есть, вместе с `modelUsage`, но в сумму не входит. `status` показывает `usage`: для каждого помощника `known_runs` (полностью известные запуски), `partial_runs` (известна нижняя граница), `unknown_runs` и `at_least` — сумму известного. Это токены по данным CLI, а не стоимость и не полный расход.

**Хранение.** Каталог состояния лежит вне проекта. В нём остаются состояние задачи, полные запросы и тексты для модели, необработанные ответы и вывод CLI (stdout и stderr), вывод проверок и `final.md`. Для задач, которые ведёт Codex, записи беседы хранятся в `~/.local/state/codex-claude-council/conversations`, в том числе после завершения. Автоматически ничего не удаляется. Эти файлы могут содержать материалы проекта и сведения из вывода CLI, поэтому каталог должен оставаться закрытым.

**Диагностика.** После неудачного вызова или делегированного исправления `status` показывает в `last_failure` операцию (`call` или `repair`), класс ошибки (`AUTH`, `LIMIT`, `TRANSIENT`, `NETWORK`, `TRANSPORT`, `TIMEOUT` и другие причины процесса, `REPORT`, а у исправления ещё `SCOPE` — изменения вне плана или в Git) и путь к сохранённому stderr. `NETWORK` (сеть недоступна, имя не разрешается, соединение отклонено) не даёт права на повтор через `--retry-of`: сначала нужно восстановить соединение. Хвост stderr без управляющих кодов терминала, не больше 500 байт, выводится только по `status --diagnostics`. Удаление секретов из него не гарантируется.

**Повтор после сбоя.** Тот же вызов можно повторить без изменений, только если доказано, что запрос не дошёл до модели: процесс помощника не удалось запустить; Claude вернул отказ входа точно известного вида с нулевым расходом (он описан в `references/local-transport.md`); адаптер Codex завершился до отправки хода и оставил контрольную точку `NOT_STARTED`. Это действует и для новой беседы, и для уже идущей: новая начинается заново с тем же идентификатором, идущая продолжается. Claude сохраняет неудачный запрос и ответ об отказе входа в записи беседы; видит ли их модель при продолжении, не проверялось. Если запрос мог дойти до модели, одинаковый вызов останавливается: кратковременный сбой связи повторяется через `--retry-of`, в остальных случаях нужна различающая проверка или другая цель.

## Границы переносимости

Состояние привязано к абсолютному пути проекта, а сессия Claude хранится его установленным CLI. Перемещение папки или другой компьютер не являются обычным продолжением без проверки путей и доступности сессии. Автоматической синхронизации нет.

В Git учитывается корень рабочего дерева. Если чат открыт в подпапке, Codex должен определить корень, а не передавать подпапку как отдельный репозиторий. Подмодули и ссылки на каталоги не пропускаются молча: текущий контроллер останавливается и требует отдельного определения проверки. Для проекта без Git полноту входов определяют scope, файлы требований и маршрутов.


### Обновление до 1.5.0

Задачи, созданные раньше, продолжаются без изменений, и их помощник по-прежнему наследует всё окружение. Новые задачи создаются в версии состояния 6, которую 1.4.5 и более ранние версии не откроют. Если помощнику новой задачи нужна переменная сверх базовых, добавьте её имя: `env --task … --pass-env NAME`. [Описание версии](releases/1.5.0.md).

### Обновление до 1.4.5

Задачи продолжаются без пересоздания. Указание исправить отклонённый отчёт передавайте в `--correction`, а не в `--goal`: другая цель, другой `--exchange` или другой контекст Git теперь всегда означают новое исследование. Шаблоны команд `review` и `adversarial-review` ставят перед аргументами маркер `--exact-args`. `status` показывает `final_report` и `last_failure`; хвост вывода помощника — только по `status --diagnostics`. Не возвращайтесь к версии до 1.4.5, если `finalize` мог прерваться. [Описание версии](releases/1.4.5.md).

### Обновление до 1.4.4

Активная или ожидающая запись беседы Codex теперь закрывается сама после `finalize` со статусом `PASSED` (иначе `finalize` сообщает, что запись осталась открытой), а карточка восстановления читает текущий ход задачи Council. После прерывания запись остаётся на паузе, а карточка велит продолжить работу, только если пользователь об этом попросит. Если в ходе произошло сжатие контекста, перед окончанием ответа обработчик один раз просит сверить последнюю просьбу пользователя с тем, что сделано. Чистое ревью принимается только для тех результатов проверок, которые проверяющий видел пройденными и актуальными, с тем же способом, командой, утверждением и содержимым. Задачи и записи, созданные раньше, продолжаются без пересоздания. [Описание версии](releases/1.4.4.md).

### Обновление до 1.4.2

Установщик добавляет порядок восстановления в глобальные инструкции Codex. Если после смены контекста текущее поручение отсутствует, ведущий находит запись именно этого чата, сверяет её с последним реальным запросом и продолжает сохранённый шаг. Завершённая запись старой задачи не считается новым поручением. Прежние инструкции сохраняются с резервной копией, повторная установка не дублирует блок.

В беседе, в которой готовилось исправление, проверена реальная смена контекста: ведущий самостоятельно продолжил исходное поручение без напоминания пользователя и без нового запуска помощника. Состояние помощника, его сессии и счётчики не изменились. Это подтверждает проверенный сценарий, а не все возможные сеансы.

Точная внутренняя причина недоставки событий штатными обработчиками Codex в проверенной беседе не установлена. Исправление использует независимый путь через глобальные инструкции и не подтверждает исправление самих обработчиков. Проверка их регистрации в отдельном процессе не доказывает доставку событий в уже открытый чат. [Описание версии и проверок](releases/1.4.2.md).

### Обновление до 1.4.1

Глобальная установка теперь подключает восстановление через общие пользовательские обработчики Codex. Настройка каждого проекта и отдельная команда создания записи беседы не нужны: обычный запуск Council автоматически сохраняет привязку. Ведущий агент выполняет установку и проверяет загрузку; от пользователя не требуется создавать файлы настроек. Обработчики не вмешиваются в беседы, где Council не используется.

### Обновление до 1.4.0

Для новой задачи нужно явно указать `preservation`: пустой объект, если условий неизменности внешнего состояния нет, либо условия с читающими проверками состояния. При наличии таких условий исходное состояние фиксируется до первого воздействия. Старые задачи продолжаются по прежним правилам, без выдуманной исходной фиксации. Поставляемый пример обновлён и включён в локальную установку.

В 1.4.0 восстановление требовало отдельного подключения. В 1.4.1 глобальная установка и запуск Council выполняют эти шаги автоматически; подробнее в [инструкции восстановления](../references/conversation-recovery.md).

### Обновление до 1.3.2

Продолжайте существующую задачу по её сохранённому пути: повторный `init` не нужен. Версии состояния 1–3 сохраняют прежнюю привязку к снимкам; новые задачи используют привязку к содержимому. Формат новых ответов помощника становится структурированным в обоих направлениях. Старые исходные ответы остаются неизменными.

В `status` отдельно видны предварительные находки из отклонённых ответов и повторно использованные проверки. Исправление отчёта выполняется обычным следующим `call` в той же сессии; режим и диагностику контроллер передаёт сам. Никакая предварительная находка или восстановленная попытка не заменяет окончательный `PASSED`.
