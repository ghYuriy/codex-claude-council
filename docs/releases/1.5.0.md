# Версия 1.5.0: окружение помощника и учёт расхода

## Окружение помощника

- **Только вход по подписке.** Помощник входит только через сохранённый вход своего CLI по подписке: `/login` в Claude Code, `codex login` через ChatGPT. Других способов входа Council не поддерживает.
- **Только нужные переменные.** Раньше процесс помощника наследовал всё окружение ведущего: переменные входа, идентификаторы сессии ведущего и любые другие переменные, заданные при запуске. Теперь помощник задачи, созданной в 1.5.0, всегда получает только пути, локаль, временный каталог, прокси и сертификаты, собственные настройки CLI (выбор модели и усилия, клиентский сертификат, отказ от телеметрии), расположение сохранённого входа (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) и имена, добавленные для задачи или вызова. CLI для этого не запускается, файлы настроек не читаются и не меняются.
- **Другие способы входа и сессия ведущего закрыты.** Из собственных пространств имён CLI (`ANTHROPIC_*`, `CLAUDE*`, `OPENAI_*`, `CODEX_*`) к помощнику попадают только перечисленные настройки и расположение сохранённого входа, а добавить оттуда нельзя ни одной переменной: `init --pass-env`, `env --pass-env` и `COUNCIL_PASS_ENV` с таким именем останавливают команду до запуска помощника. Так закрыты и ключи, токены, другие адреса API и облачные поставщики, и идентификаторы сессии ведущего (`CODEX_THREAD_ID`, `CODEX_COMPANION_*`, `CLAUDECODE`, сессионные `CLAUDE_CODE_*`), включая переменные, которые появятся в новых версиях CLI. Так же отвергается `AWS_BEARER_TOKEN_BEDROCK` — токен входа через Bedrock вне этих пространств. Остальные добавленные имена передаются как есть: переменную проекта Council не отличает от переменной, которую CLI читает без своего префикса (например, `API_TIMEOUT_MS` у Claude). Это важно и для Claude: в режиме `-p` ключ из окружения используется даже поверх сохранённого входа.
- **Вход самого CLI.** Сохранённый вход и файлы настроек CLI Council не меняет, поэтому сам CLI должен быть входом по подписке. `/codex-claude-council:setup` теперь считает Codex готовым только при входе через ChatGPT и поставщике моделей OpenAI: при сохранённом ключе API, другом поставщике (даже со входом ChatGPT) или поставщике, который не удалось прочитать, он сообщает, что нужно войти через `codex login`, и больше не предлагает вход по ключу. Если для проекта уже работает общий процесс Codex, setup проверяет его, а помощник всегда запускает свой. Поставщик, заданный в `env` настроек Claude, тоже не поддерживается.
- **Добавление имён.** `init --pass-env NAME` — для всей задачи; `council.py env --task … --pass-env NAME` — для существующей задачи без нового `init`, с теми же счётчиками и сессиями, с записью в журнал; `COUNCIL_PASS_ENV=NAME1,NAME2` — только на текущий вызов, в задачу такие имена не сохраняются; задачи до 1.5.0 эту переменную не учитывают. Имя из пространства имён CLI или недопустимое имя останавливает команду до запуска помощника.
- **Только имена.** Состояние задачи, `job.json` и запись запуска хранят имена переменных, но не значения. Процесс, запускающий помощника, собирает окружение заново из своего окружения, и Codex получает записанные имена; система может добавить свои служебные (в macOS — `__CF_USER_TEXT_ENCODING`). Необработанный вывод CLI в каталоге задачи может содержать значения, поэтому обычный `status` его не показывает.
- **Сбой входа.** Сообщения установленных CLI о входе («Not logged in · Run /login», «Please run /login», «Not signed in. Please run 'codex login'», истёкшая сессия) распознаются как ошибка входа, и `last_failure` подсказывает войти через `/login` или `codex login` и повторить вызов, а для переменной проекта — команду `env`. Повтора с другим окружением или другим способом входа нет.
- Фильтр касается только запусков помощника: обсуждений, ревью и делегированного исправления. Проверки проекта и сборщики сохранности получают окружение как прежде.

## Повтор вызова, не дошедшего до модели

- **Ошибка прежних версий.** Если в беседе уже был ответ, а следующий вызов доказуемо не дошёл до модели, повторить его без изменений было нельзя: защита от одинаковых запросов его останавливала. Причина — контроллер записывал факт «вызов не дошёл до модели» только вместе со сбросом самой беседы, а сброс допустим лишь для беседы, которая ещё не начиналась.
- **Теперь факт о вызове записывается отдельно от состояния беседы.** Тот же вызов можно повторить без изменений; беседа, которая ещё не начиналась, начинается заново с тем же идентификатором, а уже идущая продолжается со своим. Доказательства прежние, но действуют и в идущей беседе: процесс помощника не удалось запустить; Claude вернул точный отказ входа с нулевым расходом; адаптер Codex завершился до отправки хода. Адаптер Codex теперь оставляет контрольную точку `NOT_STARTED` и тогда, когда сбой случился при продолжении беседы. Решение принимается по записанному доказательству при каждом вызове, поэтому учитываются и такие сбои, сохранённые прежними версиями.
- **Состояние беседы — тоже из доказательств.** Сбой запуска процесса ничего не говорит о беседе, поэтому больше не сбрасывает её: если Claude уже подтвердил, что беседа с этим идентификатором существует, следующий вызов продолжает её, а не пытается создать заново.
- **Граница.** Если запрос мог дойти до модели, одинаковый вызов по-прежнему останавливается. Потерянная беседа Claude («No conversation found») при уже идущей беседе тоже не даёт права на повтор: повтор её не вернёт, а новую беседу Council сам не начинает. Сбой запуска, который `recover` версии до 1.4.2 восстановил без записи результата процесса в сам запуск, тоже остаётся неоднозначным: результат не сохранён в записи запуска, а неизменность оставшегося `process.json` подтвердить нельзя, поэтому Council не принимает его как доказательство.

## Учёт расхода

- **Claude.** Запуск записывает `usage` этого вызова из ответа CLI как есть, а суммирует четыре счётчика токенов; если какого-то нет или нет самого `usage`, расход запуска в сумме считается неизвестным, а полученное, включая `modelUsage`, всё равно сохраняется. Накопленное по сессии `modelUsage` хранится отдельно и со значениями отдельных вызовов не складывается.
- **Codex.** Адаптер записывает накопленный по беседе счётчик в `usage.json` рядом с запуском, отдельно от контрольной точки сессии. Расход запуска — разность счётчика в конце хода и до его начала. Новая беседа начинается с нуля; у продолжения начальная точка — значение, которое app-server повторяет перед новым ходом. Повторные события не учитываются дважды; события других бесед не учитываются, в том числе пришедшие до того, как стала известна своя.
- **Неизвестное остаётся неизвестным.** Расход записывается как `null`, а не ноль, если события не пришли, если начальная точка продолжения неизвестна или если счётчик уменьшился — до хода, внутри хода или ниже последнего значения, которое видел любой прежний запуск той же беседы, даже с неизвестным расходом. Прерванный запуск сохраняет последнее полученное значение, в том числе после `recover`, но как нижнюю границу (`complete: false`). Отклонённый отчёт всё равно записывает расход вызова, но расход на приёмку не влияет.
- **`status`** показывает `usage`: для каждого помощника `known_runs` (полностью известные запуски), `partial_runs` (известна нижняя граница), `unknown_runs` и `at_least` — сумму известного. Это токены по данным CLI, а не стоимость.

## Проверка на установленных CLI

На Claude Code 2.1.310 и codex-cli 0.164.0 выполнены новый запуск и продолжение, каждый с полным окружением и с одними `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR` и `LANG`:

- оба сохранённых входа работают с сокращённым окружением;
- пользовательские и проектные инструкции загружаются в обоих случаях, а изменённый файл проекта при продолжении перечитывается;
- у Codex-помощника запускаются пользовательские hooks и MCP-серверы Codex;
- у Claude в двух сессиях с одной моделью `modelUsage` после продолжения было равно прежнему значению плюс `usage` нового вызова по всем четырём счётчикам; у Codex в наблюдавшемся продолжении app-server сначала повторил событие прошлого хода, и расход нового хода был равен разности накопленных значений;
- ключ из окружения в режиме `-p` используется Claude даже поверх сохранённого входа;
- Claude Code 2.1.310 без сохранённого входа отвечает одинаковым отказом с нулевым расходом и в новой беседе, и при её продолжении, а неудачный запрос и ответ об отказе сохраняет в истории беседы.

Начальная точка продолжения Codex берётся из значения, которое повторяет сам сервер, а не из записанного Council. Поэтому и после прерванного запуска начало следующего известно, и его расход — разность одного серверного счётчика. Расход становится неизвестным, если повтор ниже последнего значения, которое видел прежний запуск той же беседы.

Факты записаны в `references/local-transport.md`.

## Совместимость

- Новые задачи создаются в версии состояния 6. Версия 1.4.5 и более ранние отказываются её открывать.
- Задачи версий 1–5 не переводятся в версию 6 и продолжаются по прежним правилам: их помощник наследует всё окружение, команда `env` для них не применяется, `COUNCIL_PASS_ENV` не учитывается.
- В тестах переменные подменных CLI передаются явно через `COUNCIL_PASS_ENV`.

## Что проверено

- Тесты используют подменные программы и не обращаются к моделям. Подменный Codex отдаёт события расхода в форме, наблюдаемой у установленного app-server, включая повтор при продолжении, а также необычные последовательности: уменьшение счётчика внутри хода, запоздалый повтор, событие чужой беседы до своей, продолжение ниже прежнего значения. Тест подтверждает, что Council не запускает CLI для проверки входа (например, `claude auth status`).
- Python: 343 теста (280 прежних и 63 новых), все прошли в полном прогоне. Прежние тесты передают переменные подменных CLI через `COUNCIL_PASS_ENV`.
- Встроенный компонент: 135 тестов, все прошли; после прогона не осталось новых фоновых процессов. Адаптер Codex с учётом расхода проверяется сквозными тестами Python через подменный Codex.
- Каждое новое поведение сначала проверено падающим тестом.
- Не проверено: поведение на Linux при реальном входе; соответствие расхода счёту у поставщика; ответ установленного Claude при отказе входа в беседе, где уже был ответ модели (проба шла без входа с самого начала; если ответ отличается, повтор останется заблокированным).
