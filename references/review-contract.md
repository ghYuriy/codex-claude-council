# Review contract and limits

The controller supplies `task_id`, `phase`, `stage`, `request_id`, `code_snapshot_id`, the exact original task, relevant requirements, macro/micro work plan, required files, current check metadata, artifact root and complete snapshot-material paths. Initial version-2/version-3 DESIGN, CONSULT and REVIEW requests omit earlier model positions/issues and advertise only the evidence subtree via `evidence_root` and `--add-dir`. To open a task-relative evidence reference, remove `evidence_reference_prefix` from its start and join it to `evidence_root`; keep the `evidence/` prefix when citing it. The critic is instructed not to open task state, issue/transcript files, previous reviews or other sessions during that first assessment. This is omission plus an explicit instruction, not filesystem read confinement. Subsequent calls include updated evidence, open issues and optional argument exchanges, expose the task artifacts and resume the saved UUID. Original requirements remain available throughout.

The machine-readable schema is the single `REPORT_SCHEMA` constant in `scripts/council.py`; the controller passes it through Claude’s `--json-schema` or the Codex adapter’s output schema and independently checks the returned structure. The adapter also verifies the actual native Codex session ID. It accepts the CLI's `structured_output`, or an exact JSON object in `result`. Markdown fences and ordinary text are not accepted.

The CLI envelope must have exit code 0, `type: result`, `subtype: success`, `is_error: false`, the expected session UUID and no reported permission denial. Missing final output, max-turns termination, a timeout, malformed JSON or a successful-looking partial answer cannot count as review. Schema correctness is only a shape check.

Each report contains:

- Matching task/request/phase/snapshot IDs and verdict `CLEAR`, `CHANGES_REQUIRED`, `NEEDS_CONTEXT` or `NEEDS_DECISION`.
- Exactly one coverage entry per requested requirement, including status `satisfied`, `violated` or `unverified`, explanation and evidence references.
- All required inspected files, actual inspection actions, explicit limitations and unverified parts. Evidence names project-relative files, task-relative recorded evidence artifacts, or `check:<declared-id>`. File references can include `:line` or `:start-end`. The controller verifies existence, real line bounds, snapshot identity and retained artifact hashes. Arbitrary files outside these recorded inputs are rejected.
- Concrete issues with stable ID, requirement IDs, category, severity, claim, project-relative file location, snapshot, evidence, failure scenario, suggested distinguishing check, recommendation, uncertainties, initial `OPEN` status and a root-cause key. Put symbols/lines in the claim when applicable and only when actually read.
- Explicit closures naming a known issue, `VERIFIED_FIXED` or `REJECTED_WITH_EVIDENCE`, current related passing check references and a reason. A closure requires the corresponding earlier implementer decision and never deletes the issue history.

`CLEAR` cannot contain a violated/unverified criterion, an unverified item or a new issue. Nonblocking limitations remain in the final report; they cannot contradict a satisfied criterion or conceal missing work. The leading host must assess this semantic boundary. The controller runs the recorded checks and verifies file hashes itself. Claude's inability to rerun commands under its read-only permissions is recorded as a limitation, not automatically as an unfulfilled product criterion. Missing or insufficient evidence is still unverified. The controller cannot verify whether the reviewer read a file merely because it appears in `inspected_files`, whether a claim is correct, whether the check is sufficient, or whether a saved quoted user decision is authentic.

Historical manifests and recorded check outputs may support before/after comparisons. Their original hashes and known snapshot IDs must validate. Each requirement or finding still needs current evidence, and issue closure must include a current related passing check performed after the fix/dispute. An old passing result cannot replace a current missing, failed or interrupted check.

All registered issues are treated conservatively as requiring a recorded resolution before final acceptance, including low-severity issues. A new serious defect near the budget limit is still registered and reported. Repeating the same request or unresolved issue keys with unchanged artifacts stops the exchange. This detects literal/structural repetition, not every disguised semantic loop. A new check artifact can represent progress without a code change, but rerunning an identical check just to extend a debate is not meaningful progress.

The first review covers specification and implementation quality. A follow-up focuses on closure and repair regressions; it is not an instruction to invent more findings. If the reviewer is right, change the implementation or decision based on evidence. If the reviewer suggests a harmful repair, preserve correct behavior and present the counterexample. Neither model's status settles a factual dispute.

The same critic instructions reach both providers. Apply the [quality contract](quality-contract.md) to the question's premises as well as the proposed answer. Use existing coverage explanations for a consequential decision's basis, strongest feasible alternative, material counterargument and observable invalidation condition. A follow-up identifies what evidence changed the position. These are inspection instructions, not new JSON fields or extra approval rounds; schema validation cannot prove adherence or reasoning quality.

In DESIGN/CONSULT, coverage states whether the proposed design or answer resolves the stated question against each requirement, not whether future implementation is complete. Explain the proposed behavior and supporting source evidence; do not claim that unperformed implementation or tests passed. Planned work alone is not a defect or missing investigation context. Missing facts needed to decide the question, actual defects and unresolved user decisions still block CLEAR. In REVIEW, coverage concerns the actual completed result and its current evidence. A resolved design never substitutes for implementation checks or REVIEW. For version-2 and version-3 tasks, each session/topic must have its own complete, intact CLEAR response before final acceptance, and each block's sessions must meet that rule before checkpoint. Another session's result cannot erase missing facts or a required decision, even if the blocking report registered no issue. Resume the original session with new evidence or the actual saved user decision. CLEAR never replaces a user's authorization or permission to accept a material risk. The JSON schema and counters enforce structure, not the semantic honesty of a claim or the sufficiency of a test.

## Preserving fixes and changing the repair strategy

These rules apply to both leading hosts. Retain canonical issue IDs, occurrences and previous closure evidence. When a VERIFIED_FIXED issue returns, identify the actual counterexample and distinguish it from a newly discovered defect. A closing check becomes a preservation obligation at subsequent acceptance, including when its original requirement was optional. The implementer must keep the regression scenario in the check; the reviewer assesses whether that check still proves the behavior.

A worsening or stagnant repair follows [repair-control.md](repair-control.md). A delegated Codex repair cannot approve itself. In the Claude-led direction only, a separate read-only Claude review verifies that bounded repair with the same report schema, current checks, issue-closure conditions and PASSED gate. Findings based on preference or unverified assumptions remain disputable; there is no obligation to manufacture a patch or reach model agreement.

The block review explicitly replaced by a verified repair intervention is the only supersession exception. The replacement must cover every scoped requirement and outstanding issue with fresh checks. Original DESIGN/CONSULT decisions are not superseded.
