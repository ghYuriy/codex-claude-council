# Review contract and limits

The controller supplies `task_id`, `phase`, `stage`, `request_id`, `code_snapshot_id`, the exact original task, relevant requirements, macro/micro work plan, required files, current check metadata, artifact root and complete snapshot-material paths. Ordinary initial version-2 and later DESIGN, CONSULT and REVIEW requests omit earlier model positions/issues and advertise only the evidence subtree via `evidence_root` and `--add-dir`. To open a task-relative evidence reference, remove `evidence_reference_prefix` from its start and join it to `evidence_root`; keep the `evidence/` prefix when citing it. The critic is instructed not to open task state, issue/transcript files, previous reviews or other sessions during that first assessment. This is omission plus an explicit instruction, not filesystem read confinement. Until this session has an accepted COMPLETE report, corrections keep the same independent perspective, empty accepted-issue list and evidence-only root. Only this session’s own rejected answers and candidates are added, through retained copies in evidence/. After acceptance, calls include updated evidence, open issues and optional exchanges and resume the saved UUID. These advertised roots are not OS read confinement. Original requirements remain available throughout. A narrowed DESIGN/CONSULT validates coverage only for its supplied requirement selection; its result cannot substitute for a complete stage REVIEW or drop other discussions or issues. The controller retains the full intake and final acceptance obligations.

The request records `report_format` and its exact `output_schema`, generated by `report_schema` in `scripts/council.py`. New calls use format 2 in both directions, including resumed legacy tasks, except format 3 in sessions with analysis units (below). Old saved requests without that field retain format 1 and their original string references. The controller passes the schema through Claude’s `--json-schema` or the Codex adapter and uses one error collector for both shape and semantic validation. Since 1.4.5 the saved `request.json` keeps the full request, including `critic` and `output_schema`, while the helper receives `prompt.json`: the same request without those two fields, whose hash is recorded as `prompt_sha256`. The instruction and schema travel only through the transport's own channel: Claude's `--append-system-prompt` and `--json-schema`, or the Codex adapter's `--contract`, which reads them from the saved request and refuses a prompt that repeats them. `contract_notes` contains the base reference rules, plus candidate rules only when candidates are supplied and rejected-report rules only with `report_feedback`. Earlier saved requests are not rewritten. The adapter also verifies the actual native Codex session ID. It accepts the CLI's `structured_output`, or an exact JSON object in `result`. Markdown fences and ordinary text are not accepted.

Since 1.5.2 every new request records `contract_version` and is validated against the exact schema saved with it, with the facet rules of that version; requests without the field keep their earlier branch. A call that sends analysis units, and every later call of a session that has units, uses report format 3. Format 3 adds `position_changes` (`prior_request_id`, `prior_position`, `new_position`, `evidence`) and, when units are sent, `analysis` (one required array per facet of the call, one result per unit with `unit_id`, `status`, `explanation`, `evidence`, `issue_ids` and the facet's own fields). Booleans are checked as booleans. The facet rules are in the [protocol](protocol.md); correcting one's own rejected report is not a position change.

The CLI envelope must have exit code 0, `type: result`, `subtype: success`, `is_error: false`, the expected session UUID and no reported permission denial. Missing final output, max-turns termination, a timeout, malformed JSON or a successful-looking partial answer cannot count as review. Schema correctness is only a shape check.

Copy exact paths into `inspected_files`, without line ranges or explanations. Evidence and `issue.location` use flat reference objects:

```json
{"kind":"file","path":"src/example.py","check_id":"","start_line":4,"end_line":7,"explanation":"The checked boundary"}
```

```json
{"kind":"check","path":"","check_id":"unit","start_line":0,"end_line":0,"explanation":"Recorded regression result"}
```

For a whole file, both line fields are zero. Otherwise both are positive inclusive bounds. A check uses its declared ID, not a directory UUID; its path is empty and bounds are zero. The request supplies ready-to-copy objects in `check_references`. `issue.location` must be a project-file reference. An explanation cannot make an unknown path or check admissible. The wire schema uses basic JSON types; the same controller validates line bounds and unused fields. Raw answers are retained unchanged.

On rejection the single collector returns all safely inspectable shape, reference and semantic errors, including exact missing files. It skips unsafe malformed subtrees but still checks independent valid fields. The next explicit call to that same session gets `report_feedback` and a hash-verified copy of the rejected answer. A later transport failure does not erase the earlier report diagnostics. With unchanged goal, follow-up exchange (`--exchange`), content, Git context, check evidence and preservation conditions, `mode: correct_report` directs repair of the existing answer using completed inspection; only missing inspection or evidence repair needs new reading. Any changed input, including a different `--goal`, produces `mode: reassess`. An instruction for repairing the report goes in `--correction`; it is passed to the helper as `correction`, never changes the goal and is not compared when choosing the mode. Neither mode adds an automatic model call, accepts a partial answer or promises a measured speedup.

Rejected findings appear separately in `candidates.json` and `status.pending_candidates`, with their original occurrences and source hashes. They do not enter the accepted issue ledger or establish approval. Every pending candidate supplied to a session needs one `candidate_resolutions` entry in an otherwise admissible report: `candidate_id`, `action` (PROMOTE or WITHDRAW), `issue_id`, `reason`, and structured `evidence`. PROMOTE names a finding in that validated report. WITHDRAW uses an empty issue ID and explains the withdrawal with current evidence. Unknown, duplicate or missing resolutions are rejected. A candidate cannot be closed through `closed_issues`. Pending candidates and changed source/resolution artifacts prevent acceptance; final.md retains the dispositions.

Independent discussions may choose the same local issue ID for different findings. The controller preserves a distinct canonical ledger ID on collision, records `issue_id_aliases`, and keeps the raw report unchanged. Later calls use supplied ledger IDs. Matching cause keys retain the canonical identity; semantic duplicates with different keys still need judgment. A candidate promotion cannot repurpose a supplied accepted ID for another cause. Legacy unresolved rejected reports are derived from their hash-verified raw output when the selected task is read; ordinary read-only status does not rewrite state. Previously accepted legacy discussions are not retroactively reopened.


Each report contains:

- Matching task/request/phase/snapshot IDs and verdict `CLEAR`, `CHANGES_REQUIRED`, `NEEDS_CONTEXT` or `NEEDS_DECISION`.
- Exactly one coverage entry per requested requirement, including status `satisfied`, `violated` or `unverified`, explanation and evidence references.
- All required inspected files, actual inspection actions, explicit limitations and unverified parts. Structured references name project-relative files, task-relative recorded evidence artifacts, or declared checks, with line bounds in separate fields. Legacy saved format-1 references retain their original syntax. The controller verifies existence, real line bounds, snapshot identity and retained artifact hashes. Arbitrary files outside these recorded inputs are rejected.
- Concrete issues with stable ID, requirement IDs, category, severity, claim, project-relative file location, snapshot, evidence, failure scenario, suggested distinguishing check, recommendation, uncertainties, initial `OPEN` status and a root-cause key. Put symbols/lines in the claim when applicable and only when actually read.
- Explicit closures naming a known issue, `VERIFIED_FIXED` or `REJECTED_WITH_EVIDENCE`, current related passing check references and a reason. A closure requires the corresponding earlier implementer decision and never deletes the issue history.

`CLEAR` cannot contain a violated/unverified criterion, an unverified item or a new issue. Nonblocking limitations remain in the final report; they cannot contradict a satisfied criterion or conceal missing work. The leading host must assess this semantic boundary. The controller runs the recorded checks and verifies file hashes itself. Claude's inability to rerun commands under its read-only permissions is recorded as a limitation, not automatically as an unfulfilled product criterion. Missing or insufficient evidence is still unverified. The controller cannot verify whether the reviewer read a file merely because it appears in `inspected_files`, whether a claim is correct, whether the check is sufficient, or whether a saved quoted user decision is authentic.

Historical manifests and recorded check outputs may support before/after comparisons. Advertised `evidence/rejected-<request-id>/stdout.json` copies may also be listed and cited: they must match the recorded response hash of a known run and always count as historical context, even when the source snapshot is unchanged. Their original hashes and known snapshot IDs must validate. Each requirement or finding still needs current evidence, and issue closure must include a current related passing check performed after the fix/dispute. An old passing result cannot replace a current missing, failed or interrupted check. Under protocol 4, an intact check may remain current across changes limited to explicitly declared exclusions; the dependency fingerprint and any reuse are shown by the controller. The reviewer must assess whether the exclusions are truly irrelevant.

All registered issues are treated conservatively as requiring a recorded resolution before final acceptance, including low-severity issues. A new serious defect near the budget limit is still registered and reported. Repeating the same request or unresolved issue keys with unchanged artifacts within one discussion stops the exchange. A first independent REVIEW is not a repetition of DESIGN merely because it observes the same issue. This detects literal/structural repetition, not every disguised semantic loop. A new check artifact can represent progress without a code change, but rerunning an identical check just to extend a debate is not meaningful progress.

The first review covers specification and implementation quality. A follow-up focuses on closure and repair regressions; it is not an instruction to invent more findings. If the reviewer is right, change the implementation or decision based on evidence. If the reviewer suggests a harmful repair, preserve correct behavior and present the counterexample. Neither model's status settles a factual dispute.

The same critic instructions reach both providers. Apply the [quality contract](quality-contract.md) to the question's premises as well as the proposed answer. Use existing coverage explanations for a consequential decision's basis, strongest feasible alternative, material counterargument and observable invalidation condition. A follow-up identifies what evidence changed the position. These are inspection instructions, not new JSON fields or extra approval rounds; schema validation cannot prove adherence or reasoning quality.

In DESIGN/CONSULT, coverage states whether the proposed design or answer resolves the stated question against each requirement, not whether future implementation is complete. Explain the proposed behavior and supporting source evidence; do not claim that unperformed implementation or tests passed. Planned work alone is not a defect or missing investigation context. Missing facts needed to decide the question, actual defects and unresolved user decisions still block CLEAR. In REVIEW, coverage concerns the actual completed result and its current evidence. A resolved design never substitutes for implementation checks or REVIEW. For version-2 and later tasks, each session/topic must have its own complete, intact CLEAR response before final acceptance, and each block's sessions must meet that rule before checkpoint. Another session's result cannot erase missing facts or a required decision, even if the blocking report registered no issue. Resume the original session with new evidence or the actual saved user decision. CLEAR never replaces a user's authorization or permission to accept a material risk. The JSON schema and counters enforce structure, not the semantic honesty of a claim or the sufficiency of a test.

## Preserving fixes and changing the repair strategy

These rules apply to both leading hosts. Retain canonical issue IDs, occurrences and previous closure evidence. When a VERIFIED_FIXED issue returns, identify the actual counterexample and distinguish it from a newly discovered defect. A closing check becomes a preservation obligation at subsequent acceptance, including when its original requirement was optional. The implementer must keep the regression scenario in the check; the reviewer assesses whether that check still proves the behavior.

A worsening or stagnant repair follows [repair-control.md](repair-control.md). A delegated Codex repair cannot approve itself. In the Claude-led direction only, a separate read-only Claude review verifies that bounded repair with the same report schema, current checks, issue-closure conditions and PASSED gate. Its first request uses `perspective: handoff_verification`: it deliberately includes the issue ledger, while advertising only the primary evidence subtree. Independence means independent verification of the repair author’s work, not ignorance of the issues being closed. Inspect the supplied ledger and primary files/checks, not state/transcripts or other model reports in `reviews/` or `repairs/`. Later calls resume that verification session using the ordinary follow-up rules. Findings based on preference or unverified assumptions remain disputable; there is no obligation to manufacture a patch or reach model agreement.

The block review explicitly replaced by a verified repair intervention is the only supersession exception. The replacement must cover every scoped requirement and outstanding issue with fresh checks. Original DESIGN/CONSULT decisions are not superseded.


For a declared preservation requirement, inspect `preservation_evidence`, its collector program, the immutable baseline, every deviation and any explicit restoration or user-approved criterion change. A disclosure that a counter changed contradicts an unchanged-state criterion; it cannot be reclassified as satisfied because the reviewer considers the effect harmless. Later checks relative to a later state do not restore the original baseline. Typed preservation failures independently block checkpoint/final acceptance even if a model incorrectly returns CLEAR.

Start with `review_materials` and read all required pages. Inspect the programs behind checks as well as their output; use the retained source copies and declared dependency list. Unknown dynamic or environmental dependencies remain a stated limit. The complete technical manifest is an integrity catalogue, not a requirement to request an oversized whole-file read. Full source and requirement links remain available in a narrowed discussion; preserved conditions still apply.
